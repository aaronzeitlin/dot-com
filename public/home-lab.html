Home Lab

Home Lab grew from a household calendar bot into a self-hosted application platform and an experiment in coordinating AI-assisted software work. In early March 2026, the roadmap described eleven services sharing a server. By August, the lab also had its own agent SDK, command-line tools, dispatch records, and release checks. Today a much smaller set of household services, applications, and operational tools remains in use.

Two decisions account for much of that change. The July repository migration removed a second layer of version coordination from releases. The August reduction cut systems whose ongoing maintenance had outgrown their role in the lab.

From calendar bot to application platform

The February 2026 prototype could create calendar events from chat. Its core defined the tool interface, validated inputs, and applied access policy. A messaging adapter translated requests and replies. The first version used Matrix, then switched to Telegram. The early architecture notes treated command parsing as temporary and kept the tool interface and access rules in the core so they could continue to apply once a model selected the tools.

The March roadmap proposed using chat as a common interface to separate services. A morning briefing, for example, could combine calendar entries, recent development activity, and service health. It also proposed sharing model configuration after several applications had acquired their own copies of provider selection, caching, and fallback logic. The event bus was one of the pieces that became part of the running lab.

The runtime moved from a rented server to local hardware that spring. Docker Compose defined the services, which retained separate images and containers. The event bus addressed a specific need from the roadmap. A briefing could make synchronous requests, while a service reacting to an event needed a way to catch up after downtime. The bus writes events to SQLite before broadcasting them and lets consumers poll or replay stored events after a disconnect. Direct requests remain available for work that needs an immediate response.

Coordinating software work

An April architecture decision assigned backlog and roadmap analysis to one service and task execution to another. The planning service aggregated issues and pull requests, computed priorities, and published a feed. The execution service used that feed to propose work, then handled approval, dispatch, and task status. Each kept its own database and exchanged data over HTTP. The aim was to give the priority signal and the execution record clear owners.

The May runner started with one issue at a time. An operator allowlist limited live dispatch, and the dry-run mode reported the selected issue and the checks it would have to pass. The design records also separated authoring, review, and live verification. A successful test belonged to the change it exercised. A production change required evidence from the running system. Those requirements made completion a question of what the workflow could demonstrate.

As concurrent work increased, isolation and bookkeeping became projects in their own right. The lab’s worktree setup shared some submodule checkouts across sessions, so separate top-level worktrees could still write to the same service directory. The coordination design introduced explicit claims on the parts of the repository a session could change. In July, a SQLite run ledger replaced several mutable session and dispatch files, with append-only receipts for run evidence.

Why six repositories moved into one

The lab used independent service repositories as Git submodules and installed their code through one pnpm workspace. Git recorded which service revision to check out. The workspace and its lockfile recorded which packages built together. The July architecture decision measured the coordination cost. Of 300 Lab commits sampled from July 14 to 30, 176 updated submodule pins.

There were two recurring failures. A service merge could leave the lab pinned to an older revision, which deployment would faithfully reproduce. An incomplete submodule checkout could omit packages from a regenerated lockfile, causing a later frozen install to fail. Pointer checks and lockfile repairs made the hybrid safer to operate. Each service change still involved coordinating the service merge, the pointer update, and the build.

The decision compared keeping the hybrid, using a monorepo, and giving each repository a genuinely independent release. Independent release would have meant publishing five shared packages and coordinating dependency updates across their consumers. The monorepo kept shared code and its consumers in one commit. Runtime isolation already came from separate images and containers, which the migration preserved.

The six imports landed in stages, starting with the event bus because it had no shared package dependencies. The imports kept existing paths and Git history. The first import verified that the lockfile still listed all 19 workspace importers and passed a frozen install. One application kept a standalone backend lockfile so it could be extracted later without untangling its frontend dependencies. After a normal release succeeded on the new path, the lab removed the pointer-update bot and the checks specific to submodules.

Why the lab got smaller

By August, the dispatch machinery could give misleading answers about work it had actually completed. One incident report traced the problem to a timeout that killed the bookkeeping process while a detached worker continued. The worker could finish and open a pull request, while the status command still showed a failed job with a running worker. During the same period, six merged home-automation changes needed manual pull-and-reload steps before the running system picked them up. The code, job record, and live system were each answering a different question.

Some experimental applications had already been retired in July. The August reduction went after the machinery around the applications as well. The criterion was whether a service ran something the household relied on, protected it, or still saw regular use. The cleanup proceeded serially because it would remove the dispatcher itself. One change removed approximately 156,000 lines across 1,263 files, including the agent SDK, CLI, and dispatch bookkeeping. A separate change reduced the central documentation directory from 188 Markdown files to one operations runbook. Service-local documentation and Git history retained the material that still had a use.

The cleanup traced dependencies before deleting them. A check for a clean service tree survived because the build and deploy scripts still called it. A production smoke test survived because it inspected actual response content. The home-automation cleanup applied the same rule. One warning came from a custom log parser even though the native integration already exposed its availability. Removing the parser and its warning left one source for that state.

The monitoring decision changed during the cleanup. The initial proposal treated an external uptime monitor as sufficient. The review found that it checked host reachability and whether alerts got through, while the main stack collected service probes, resource metrics, and logs. Both were kept. Five Compose services that wrapped or duplicated monitoring were removed.

What remains in operation

The lab now centers on home automation, camera recording, monitoring, recovery, and a small set of applications. The release command compares the intended Git revision with the revision recorded on the running container, including its frontend companion where applicable. A healthy endpoint can still be serving yesterday’s build. Image builds can run on a separate worker from a clean Git archive. The worker can be replaced without restoring household data because persistent state and deployment authority remain with the runtime.

The backup design covers data that a fresh checkout and a container image cannot reconstruct. It uses PostgreSQL dumps and SQLite’s online backup API, then sends encrypted, deduplicated snapshots off-site. A restore drill unpacks a snapshot into temporary storage, checks recovered SQLite databases, and validates restored application configuration in an isolated container. This exercises the recovery path without replacing live data.

The recovery host has its own state, including the definitions for uptime checks and alert delivery. An audit found that those definitions lived only on the recovery device. The backup job was extended to capture that state through the existing backup path. The independent monitor can report an outage while the main host is down. Its own backup makes it possible to recover that monitoring setup after the recovery device fails.
