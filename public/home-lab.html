Home Lab

Home Lab started as a household calendar bot in February 2026. It grew into a self-hosted application platform, then acquired its own system for planning, dispatching, reviewing, and releasing work done by coding agents. A March roadmap described eleven services sharing a server. By August, the command-line tooling and agent SDK alone accounted for roughly 126,000 lines in the project’s inventory.

The lab now operates at a much smaller scope. Home automation, recording, monitoring, recovery, and a small set of applications remain. The Git history records how the lab reached that shape through a repository migration, the removal of its general-purpose dispatcher, and several changes to how it verifies releases and recovery.

From a calendar bot to a platform

The first prototype created calendar events from chat. Its messaging adapter translated requests and replies, while the core checked access, validated tool arguments, and recorded calls. The project switched from Matrix to Telegram within the first day of development. The early design treated the command grammar as temporary. The typed tool interface and access checks stayed in the core when a model took over tool selection.

The March roadmap proposed joining services through a common chat interface. A morning briefing could assemble calendar entries, development activity, and service health. Shared model configuration was another goal because several applications had accumulated their own provider selection, caching, and fallback logic. The proposal also included remediation suggested from health events, with approval before execution. The event bus became a running service. The roadmap’s broader self-healing loop was a separate proposal with its own dispatch and approval requirements.

The runtime moved from a rented server to local hardware in March. Deployment retained the same remote execution pattern and the existing backup strategy. Docker Compose described the running services, with separate images and containers. As applications became coupled through shared UI, authentication, and client libraries, the source layout acquired a common package workspace even while the repositories remained separate.

What the event bus guaranteed

The architecture used direct HTTP calls for requests that needed an immediate answer. Asynchronous notifications had a different requirement. A consumer that was offline when an event arrived needed a way to catch up without requiring each producer to track each subscriber.

The event bus inserts a record into SQLite before attempting to deliver it to listeners over Server-Sent Events. A disconnected client can poll or replay from a cursor, and a failed broadcast leaves the stored event available for retrieval. That makes the database the durable record of publication. Consumers still own processing, deduplication, and their replay position. The live stream provides best-effort fan-out, with bounded replay and no consumer acknowledgment protocol.

That boundary mattered to home automation. Its REST interface remained authoritative for device state. An event could prompt a faster refresh, and periodic polling still worked when the stream was unavailable. In September, the lab also changed the bus’s container health check to exercise SQLite readiness. The previous endpoint could return success whenever the HTTP process was alive, even if the service could no longer store events.

The agent orchestration experiment

An April decision gave planning and execution separate owners. The planning service aggregated issues, pull requests, and milestones into a priority feed. The execution service used that feed to propose tasks and owned approval, dispatch, and status. Each kept its own database, with HTTP carrying the priority signal and completion updates across the boundary. The intent was to let backlog policy change independently of how a worker ran.

In May, the runner began with one issue at a time. Live dispatch required an operator-approved, unexpired allowlist entry. A dry run selected a candidate and printed the checks it would have to pass. The verification design distinguished evidence by the claim being made. A focused test could support a code change, while a live behavior change required evidence from the running service. The design assigned authoring, review, and live verification to separate roles.

Parallel work exposed state that Git branches alone did not isolate in the lab’s setup. Multiple top-level worktrees could share the same service submodule checkout. The resulting design asked workers to declare the paths they intended to change. Shared decision records had a similar problem. Two workers editing one canonical file could lose each other’s changes, so the June design gave each worker a separate proposal file and used a single merge step to produce the durable record.

The July SQLite run ledger became the authority for dispatch, session, and resume state. JSON became an append-only record of what happened during a run. The migration imported the old records transactionally so existing work could still be resumed. It addressed where to read a run’s state. Two later incidents exposed how that state could still be wrong. In one, the provider’s completion event and the process exit code produced contradictory outcomes for the same run. In another, an outer timeout killed the process that recorded the final status while the detached worker kept running. Completed and deployed work could remain marked as failed with a worker still running. The two failures had different causes. One wrote conflicting outcomes, and the other never wrote a final outcome at all.

Why six repositories moved into one

Git submodules pinned the exact service revisions. A root pnpm workspace resolved shared packages from the materialized checkouts. These two graphs had to agree before a change could ship. A service merge could leave the lab pinned to an older revision, and an incomplete checkout could cause a regenerated lockfile to drop packages. In a July sample of 300 Lab commits, 176 updated submodule pins.

The decision record considered genuinely independent repositories. That model would have published five shared packages and let each service pin their versions, with deployment selecting independently built images. Frequent shared-package changes would then require version bumps across several consumers. The monorepo put the shared code, its consumers, and infrastructure configuration in one revision. Separate service images preserved runtime isolation. The cost was a shared source-access boundary, a larger checkout, and a lockfile that could serialize concurrent dependency changes.

The six imports landed in stages. The event bus went first because it had no shared package dependencies. The import swapped the submodule reference for ordinary files at the same path and preserved history. Before and after the first import, the lockfile listed the same 19 workspace importers and a frozen install passed. One application kept a standalone backend lockfile because its backend could still be extracted independently of its frontend. The lab removed pointer automation after a normal release had gone through the monorepo path.

What the reduction removed

A May review had already found experimental services that still paid for a full set of build checks, frontend checks, environment schemas, deployment wiring, and pointer updates. A capability that had moved into the household assistant could be removed as a separate service. Two other retirements were deferred in May and carried out in July. Taking a service out of Compose was only one step. Residual tests, monitoring targets, and registry entries still treated it as operational and had to be removed.

In August the project narrowed the criterion to what the household relied on, what protected it, and what still saw use. The cuts ran serially because the dispatcher itself was being removed. One change deleted approximately 156,000 lines across 1,263 files, including the agent SDK, CLI, and dispatch bookkeeping. Another cut the central documentation directory from 188 Markdown files to one operations runbook. Historical designs remained in Git, and the runbook retained the commands needed to operate the system.

The pruning followed actual callers. A clean-tree check stayed because builds and deployments depended on it. A smoke test stayed because it inspected the content of a live response. The monitoring decision also changed after reviewing the running setup. An independent uptime monitor checked whether the host and the alert path were reachable. The main monitoring stack collected service probes, resource metrics, and logs. Both served distinct failure modes, so the project kept both and removed five Compose services that wrapped or duplicated monitoring.

The household assistant retained a narrower approval path for sensitive tool calls. Its September audit found a restart case in which an already-running task could remain stranded. Startup checked for abandoned tasks only once, and a task left behind by a recent crash could still fall inside the five-minute age window. With a single executor, every running row inherited at startup belonged to the previous process. The fix marks those rows as failed immediately so they can be handled explicitly. Accepting a stored approval and creating its task happen in one database operation. Before executing the task, the system checks that the approval still belongs to the requester, remains valid, and matches the current tool version and permissions. Network failures can be retried within a fixed limit. A later experiment also reintroduced repository delegation with one job at a time and a draft pull request as its output. Its merge record describes a bounded implementation with separate runtime enablement.

What counts as a release

An August incident recorded six manual pull-and-reload cycles for home automation configuration that had already merged. Repository state and live state were separate. The gap mattered because the user-facing behavior was defined by configuration loaded by a running process.

The normal service deployment checks the image revision on the running container against the intended Git commit. It also checks the paired frontend where applicable. The expected revision comes from the source checkout, which avoids a second version file that would have to move in step with code. The release command can skip rebuilding only when the target revision is already running and healthy. When an image build runs on a separate worker, it receives a clean source archive. The runtime retains persistent data and deploy authority, so rebuilding the worker requires no household data restore.

The September audit identified a gap in the wider infrastructure path. A registry pull could fail and Compose could proceed with locally cached images. The stack could then pass health checks on old builds. The fix made a pull failure stop a full-stack deployment. Targeted service deployment kept its scoped recovery behavior. The broad infrastructure path still depends on Compose health and has no automatic stack-wide rollback. The two paths provide different verification because the scope of change and the available recovery options differ.

What counts as a backup

A May authentication outage showed why runtime configuration belongs in the recovery plan. A template sync overwrote a value that existed only in the live configuration. The running container kept using the old value until it was recreated, when authentication failed. An encrypted snapshot supplied the missing value. The replacement sync checks for live values that would be replaced by empty or placeholder entries before applying the update.

An August backup audit found a different failure. A backup job parsed the human-readable output of Docker Compose to decide if PostgreSQL was running. The status text changed, and all 105 runs in the retained log had skipped the database dump. The same investigation found that a document archive’s bind-mounted files were outside the backup set. Its metadata lived in a separate database, so restoring the media alone would have lost titles, tags, and searchable text.

The correction switched service detection to Compose’s filtered output, added the missing bind mounts and a logical database dump, and made the integrity job check for expected content in the latest snapshot. Other SQLite databases use the online backup API to capture consistent state while they are active. The backup deliberately leaves out bulky, high-churn recordings and logs. The recovery plan gives priority to the documents, databases, and configuration needed to restart the services. A successful archive check verifies the stored bytes. Coverage checks and restore drills test different parts of whether the lab can be recovered.

The recovery host’s monitoring and alert definitions were also brought into the main backup job after an audit found that they existed only on the recovery device. The restore drill unpacks a snapshot into temporary storage, checks recovered databases, and validates restored application configuration in an isolated container. The September audit verified the backup and notification path in code and left recent restore-drill execution as an evidence gap.
