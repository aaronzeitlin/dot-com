Executive summary

The Home Lab began in February 2026 as a household calendar bot. By March, a planning document described eleven services sharing a server and proposed connecting their capabilities through a common assistant. Over the next several months, the repository accumulated shared application libraries, an event bus, a release system, and a second platform for managing the coding agents that built and maintained it. The lab moved from rented infrastructure to local hardware, consolidated six repositories, and eventually removed most of the custom apparatus for coordinating software work. Household automation and a smaller group of applications continued running on the infrastructure that survived the reduction.

The most useful evidence in this history comes from the points where two parts of the system gave different answers. In July, a service's Git repository could say a change was merged while the parent repository still selected an older commit. An incomplete checkout could change which packages appeared in the shared lockfile. In August, the dispatcher could report that a worker had failed and was still running after the resulting change had been merged and deployed. A backup job could pass its archive checks while leaving a document service out of the archive and skipping a logical database dump. The September audit found similar discrepancies between process health, dependency readiness, and the revision actually serving requests.

Each discrepancy called for a different fix. The source repositories and workspace were consolidated because they represented the same release inputs. The event stream and the database stayed separate because they answered different delivery questions. Service monitoring and an independent uptime monitor survived the cuts because they observed different failures. A general-purpose agent dispatcher was retired, while narrower approval and recovery mechanisms remained useful. The resulting system is easier to describe in terms of who owns the work, who can carry it out, and what evidence establishes the outcome.

The account covers the repository record from February through November 2026. It treats roadmap scope as intent, commits as evidence of code changes, and reported tests or live checks as evidence for the cases they actually exercised. A dated audit is a snapshot of the system and its evidence at that point. The article follows later fixes where the history establishes them and gives the remaining gaps in the final section.

The first version, February 2026

A small job with a real side effect

The first commit in the assistant's history describes a Matrix bot with a Google Calendar creation tool. Its surface area was small enough to follow end to end. The adapter accepted a message from the chat transport. The core applied the access policy, selected the available tool, and validated its inputs. The calendar tool then used the account authorization to create the event. A small HTTP server handled the authorization flow and service health. The implementation included encrypted token storage and an audit record backed by SQLite.

This structure separated two kinds of change very early. Chat event formatting, connection behavior, and the rules for recognizing a message were specific to the transport. Creating a calendar event required a structured input, an authorized account, and a result the assistant could report. Keeping the latter in a tool made it possible to change how requests arrived without moving the calendar implementation into a messaging adapter. The shape also gave tests somewhere to observe the result of a call without depending exclusively on the chat client.

The early architecture notes treated the explicit command parser as temporary. They anticipated moving tool selection to a model while preserving the tool interface and the surrounding access checks. The distinction matters because changing how an action is selected does not change the permissions needed to perform it. A typed argument can be valid in shape and still request an operation outside the user's authority. Keeping both checks at an explicit boundary meant the next iteration could introduce model-driven selection without making the model the sole judge of what it was allowed to do.

The transport changed first

The same day's history contains the switch from Matrix to Telegram. The Telegram adapter used long polling. The change also adjusted the interaction policy. Matrix had used an allowlisted room plus a mention requirement. The Telegram version checked the chat against its allowlist and removed the mention requirement for the private-chat use case. The commit description calls out reauthentication friction as a motivation for changing transports. These were early product decisions about getting to a dependable household interface.

The change is also a practical check on the initial separation. The transport was swapped and policy tests changed, while the core continued to route messages to tools and retain conversation state. The Telegram commit describes an integration test spanning policy, model-driven routing, and persistence. It establishes an early tested flow across those boundaries. It provides much less evidence about what happened over weeks of ordinary use, which the early commit log does not measure.

At this point the history contains the components of a much later architectural question in miniature. A message arrives through one system, a model interprets it, a tool changes state in another system, and a log is expected to explain the result. Even a calendar entry crosses a boundary where a plausible reply and a completed operation can diverge. The later lab spent substantial effort making that distinction observable at the scale of software releases and household operations. The February implementation is the starting point for that work.

From one bot to a platform

The March plan

The March roadmap called for a common interface across a collection of services that were already colocated. Its example was a briefing that could combine calendar entries, software activity, and the health of the lab. Other proposed uses included initiating development tasks from chat and surfacing a suggested remediation after a service health event. Those features implied different forms of coupling. A briefing could assemble current answers by querying each service. A remediation workflow required a report to outlive a temporary failure, preserve its context, and reach a separate approval decision.

The roadmap also identified repeated model configuration code. Several applications maintained some combination of model selection, fallback, cached configuration, and update behavior. Sharing a configuration library could remove copies of the same behavior and give maintainers a single place to fix defaults. It also changed the relationship among consumers. A change to a shared package could affect several applications even if each application continued to build and run in its own container.

The roadmap is useful as a description of what the builder wanted the platform to become. It is a weaker source for claims about what residents could rely on. A feature listed with acceptance criteria might have been implemented in pieces, shelved, or tested only in a development path. The event bus became a service with its own code and delivery contract. The broader concept of an automatically self-healing household platform remained a larger proposal, involving separate decisions about what counted as a fault, what could be proposed, and who could approve a remediation.

Local hardware and the shared platform

By late March, the migration record says that the services had moved from a rented virtual server to local hardware. The cleanup issue tracks the work needed to retarget deployment scripts and documentation. It explicitly preserves the existing deployment pattern and backup strategy. The migration was primarily a change in where the system ran. Container definitions, application state, release verification, and the external access paths still had to be carried forward or reconciled.

Docker Compose described the runtime. Individual applications kept separate images and containers and could be restarted or released at different times. Around them, the lab provided access, configuration, monitoring, data storage, and build tooling. The later monorepo decision is easier to understand with that distinction in view. The lab could change the layout of its source and dependency graph while continuing to run the services as separate units.

The platform also introduced small shared contracts. An April pull request centralized how participating applications constructed identity headers and added common schemas for health and service events. Sharing those interfaces reduced the chance of one consumer using a different spelling or shape for a field another service treated as important. The contract described what the software expected. Each service still needed to populate the values from its own state, and deployment still needed to prove the expected revision was serving them.

The result was a platform with real reuse and substantial coordination. Shared packages changed how services were built together. APIs changed how services depended on each other at runtime. Configuration and release rules determined whether a source change reached an instance. These relationships crossed at the operator's workflow, but they served different purposes. Treating all of them as a single architecture question would obscure why a separate container could make sense even after a separate repository stopped paying for itself.

Runtime boundaries and state ownership

Ownership by capability

The September architecture audit is a useful check on what the lab actually considered canonical after the initial buildout. Home Assistant owned the physical-home state. The household assistant owned conversational policy, tool selection, and its own tasks and memory. Other retained applications had their own domain logic and persistent data. A separate journal had its own generation and recovery behavior. The event bus transported and replayed events across those boundaries. Its persistence was about what had been published, not an attempt to make one table authoritative for every connected application's state.

These ownership boundaries determined which evidence a consumer could trust. For example, a message reporting that device state changed could prompt an immediate refresh. The home-automation system remained the source for the current device state. If several messages arrived late or a subscriber missed part of a stream, the consumer could return to the authoritative interface. A notification made the view fresher. It did not transfer ownership of the underlying value.

The audit also distinguishes legitimate service separation from overlapping mechanisms. It identified parallel approval paths, placeholder interoperability tools, and generalized background machinery as candidates for scrutiny. Some applications still owned unique persistent state, real callers, or distinct failure behavior. Removing a wrapper with no active consumer and combining two services with different recovery requirements are different operations. The audit made the latter decision depend on evidence about use and ownership, which is more useful than treating container count as the primary measure of complexity.

What the repository can establish

A Compose file records declared services, dependencies, and health checks. A service being present in that file establishes that the configuration can describe it. A profile, disabled entry point, or stale deployment target may leave that service unused. The August monitoring decision surfaced a concrete instance of this difference. A monitor declared in the main stack was not the one doing independent uptime checks. The running monitor belonged to the separate recovery environment. Reading only the names in Compose would have made the two look interchangeable.

The working architecture is therefore reconstructed from several views. Service source shows how a request or job behaves. Compose shows how that behavior is intended to be deployed. The operations runbook records the intended release and recovery procedures. Live incident reports and verification comments show whether particular instances actually behaved as expected. The latest source snapshot is valuable for understanding what remains available to operate, but it does not measure live utilization or establish that every declared profile was started.

This matters especially in a small installation with a long experimental history. A dormant frontend or archived service may leave behind scripts, tests, and references that all still compile. Conversely, a small recovery script or a native integration can be operationally essential without appearing in a list of first-party applications. The later reduction put more weight on real dependencies and recoverability than on how much code a component occupied. That explains both some surprising removals and some seemingly modest tools that survived.

The event bus and its delivery contract

Persist first, notify second

The event bus serves asynchronous work that cannot be reduced to an immediate request and response. A producer posts an event. The server validates its envelope and inserts it into a SQLite database before attempting to broadcast it over Server-Sent Events. Subscribers can receive the live stream or query persisted events. If a broadcast fails because a socket disappears, the stored event remains available. The failure of a notification and the failure of publication are distinct because publication already has a durable record.

The design uses one process and one SQLite database in write-ahead logging mode. The server owns the currently connected clients in memory. That is enough to fan out updates within the deployment described by the code, and it makes a client reconnect a routine case. The design does not establish multi-instance broadcasting or an acknowledgment protocol. A subscriber that needs stronger delivery must keep track of its position, replay or poll after a disconnect, and handle repeated or missing notifications according to its own requirements.

The architecture document records two ordering mechanisms. The polling path orders by the event's logical timestamp, which the publisher may supply. Replay from a stream cursor orders by identifier. These orderings can differ, including when publisher timestamps arrive out of sequence. Identifiers are time-sortable in ordinary use, but they are not generated as a strictly increasing sequence within the same millisecond. The bus also bounds how much it replays at once. A client that moves directly to a newer live cursor after a capped catch-up can skip intermediate records. These details define the limit of the guarantee more precisely than the phrase 'durable event bus' does.

Consumers and evidence

The household state consumer illustrates the intended balance. It stores a cursor and reconnects the stream with backoff. A successfully processed event can advance that cursor. The authoritative home-automation read path still exists independently. This arrangement favors freshness when the stream is available and a usable baseline when it is not. It also avoids using a stream reconnect as evidence that a physical state change completed.

The July proof-of-life work showed a narrower claim directly. A test published a tagged event against the running bus and read it back, asserting that the marker survived the round trip. That is stronger evidence for persistence than a successful request to a health route. It does not cover every consumer's recovery behavior, the capped replay case, or the effect of restarting a subscriber between processing and recording its cursor. Those are separate properties with their own tests or documented limitations.

The September audit found that the container's health check targeted process liveness. The process could answer HTTP while its SQLite path was unusable. The follow-up changed the Docker and deployment health checks to target readiness, which exercises the database, and added regression coverage for the configuration. The service retained both concepts. A process check can help identify that the executable is running. A readiness check can help decide whether other services should rely on it for persistence.

The bus shows why the smaller lab retained some shared services. Its code has a concrete responsibility that is exercised by publishers and consumers. The contract is narrow enough to explain where an event is durable and where delivery remains a subscriber concern. That clarity survived the later pruning of speculative cross-service abstractions.

Planning and execution as separate services

The April decision

The April architecture decision placed backlog and roadmap analysis in one service and task execution in another. The planning service collected issue, pull request, and milestone data from GitHub. It could compute trends or produce a priority feed for the execution service. The execution service could use the feed to propose work and then own the approval, dispatch, and status of an individual task. The decision specified distinct databases and an HTTP boundary, with a completion callback able to refresh the planning view.

This was an ownership decision about two kinds of questions. A priority feed answers which work is worth considering. A task record answers what happened after a particular issue was selected. The facts used to rank an issue can change independently of a worker's checkout, test results, or deployment state. Giving the same service both responsibilities would have made it easier to share tables, but it would have left open which record to update as work moved from recommendation to execution.

The decision also gave each side its own health signals. Issue coverage and backlog trends were useful for evaluating the planning layer. Dispatch throughput, latency, and task state were useful for operating execution. A timely strategic dashboard could coexist with an unhealthy worker path. A running dispatcher could have no sensible task to select. The distinction is visible again in August, when task status degraded while work continued to land.

The operating cost of the split

Independent services made sense when they had distinct state and consumers. The split also created a contract to maintain. Planning and execution needed consistent issue classifications, a stable priority feed, and a way for one side to learn that the other had completed work. A change in the classification system could affect selection without any change in the runner. A callback could fail after the action it described had already completed. A single-operator lab had to maintain both the product behavior and the interface between the products.

This arrangement was part of a wider set of attempts to make the system usable from a chat interface. The proposals discussed routing development tasks and suggested remediations through the assistant, with approval before the relevant action. Those designs are useful for understanding why the planner, dispatcher, event bus, and operator controls appeared in the same project. An architectural document describing the pieces does not establish that every connection was enabled or verified together. The early runner and the later bounded delegation each have narrower implementation evidence.

The eventual reduction preserved the distinction between asking for work and giving something the authority to carry it out. It removed much of the surrounding code that turned the distinction into an all-purpose platform. That makes the April decision more informative than a component inventory. The original boundary identified a real difference between priority and execution. The project later found it could keep that difference without operating the full planning and execution stack for every workflow.

Building the autonomous runner

The first live boundary

The May runner started from a queue of eligible issues. Its first mode could choose a candidate, show which checks would apply, and exit before dispatch. The live mode initially operated one issue at a time. A subsequent pull request added an explicit operator allowlist with expiration. Dry runs remained useful because a candidate could be visible in the plan before it was authorized for live work. The gate made authorization an input with its own state rather than a phrase embedded in a worker's prompt.

The proposed first version listed reasons to stop, including unclear scope, validation failures, budget limits, and a dirty checkout. Some of the conditions protected the task itself. Others protected the surroundings in which the task ran. A clean worktree check could keep an agent from accidentally claiming local changes. A budget limit answered whether another attempt was still authorized. A stop flag gave the operator a way to interrupt future actions even if a candidate had already passed earlier checks.

A May execution record describes a bounded live run. Its recorded scope was a single allowlisted issue, with a worker surviving the supervisor's exit and producing one pull request. That is useful evidence for an execution path with a known input and a visible output. It does not establish that unattended work across other issue categories could merge or deploy safely. The project history supports a progression from dispatch, to gathering evidence, to deciding whether later actions should be enabled.

A later May change made the continuous mode finite with respect to its eligible set. Each eligible issue could be visited at most once during a session. Foreground execution could move on after the previous attempt. Background dispatch stopped after one issue so the next iteration could not overlap a detached worker. The regression tests target that distinction between advancing a queue and allowing work to run in parallel. It also shows that the word continuous described how candidates were revisited within a bounded session, with separate semantics for work that continued after the initiating process returned.

Approval was an evolving policy

The design separated the author of a change from the reviewer and the verifier for nontrivial work. The reviewer could assess scope and correctness in the diff. The verifier could examine tests or production evidence appropriate to the requested behavior. The shipper could act once the required conditions were satisfied. Even if the same person supervised those stages, the underlying claims were distinct. A diff can be correct while a deploy fails, and an endpoint can respond while running the previous version.

In June, the project changed the canonical policy to permit automatic merge and deployment after gate checks, while retaining named manual exceptions for sensitive changes. The merged pull request wired an actual merge call into the worker flow and rechecked the operator pause before invoking it. The same record left per-service deployment wiring as follow-up. The policy therefore reached further than the implementation evidence in that pull request. It establishes a change in authority and an implemented merge path, with the completeness of deployment still dependent on the service.

The change is important because the lab did not follow a simple arc from human approval to unrestricted automation and back. It tried an explicit authorization model, expanded what a passing gate could permit, and then measured what actually happened. The August incidents show why a successful merge stage could still leave work undone. The later household assistant took a narrower approach to its own tools, distinguishing reversible operations from destructive ones and privileged capabilities. Those two policy histories applied to different execution surfaces.

Parallel work, durable state, and evaluation

Worktree boundaries

One worktree per issue gave each worker a branch and an ordinary Git record of what it changed. The design record describes a failure specific to the lab's setup at the time. Separate top-level worktrees could reach a service submodule through the same physical checkout. That undermined the isolation the top-level paths appeared to provide. Concurrent edits could collide and the symptoms might only become obvious at push time. The project's response was to define explicit claims on mutation scope while it still used that layout.

The proposed claims design distinguished reading a path from writing to it. It also recognized that broad changes to shared files could overlap several narrower service claims. A claim system can make those conflicts visible before work starts, but it becomes another mechanism to enforce and maintain. Once most service sources moved into ordinary directories under the monorepo, the specific extra submodule boundary that had motivated much of the work no longer needed the same machinery.

Parallel agents had a related problem when writing project decisions. If two sessions read the same canonical file and both wrote a new version, the last writer could erase the other's addition. The June decision record introduced per-proposal files and a single promotion step. Writers could add independent inputs without rewriting the shared record. The merge step could then produce a consistent canonical output. The design applied a familiar principle from durable event processing to documentation that otherwise looked like a simple text file.

Run state and evidence

The July run-ledger change consolidated dispatch, session, lifecycle, resume, and status in SQLite. The migration imported legacy state transactionally. Run receipts became append-only records with a publication path designed to recover from a crash. The database represented the current operational state. A receipt represented evidence emitted by a particular attempt. That distinction gave the system a way to query active work without asking the worker to rewrite the only record of what it had already done.

The broader harness was evaluated with replay fixtures. Scenarios included a stalled worker, a blocked push, missing deployment evidence, an issue closed too early, and a provider failure. The scorecard included latency and recovery alongside correctness and safety. A process could appear active by sending heartbeats while making no progress on the repository. The replay harness made such a trace observable as a failure pattern. Its reported score was specific to the fixtures and rubric and should not be read as a production task success rate.

Process lifetime made recovery more complicated. A worker could leave a local commit after its terminal session stopped, before the branch reached GitHub. One retained operational note records exactly that shape of failure during the submodule period. The service-side change had already landed, but the parent repository's pointer change was still in the abandoned worktree. Relaunching from the issue alone could repeat finished work. The branch and worktree were therefore part of the evidence for deciding whether to resume, publish, or start over.

By August, a persistent record had improved the location of state but had not resolved every path that wrote it. The distinction between durable data and reliable observation is central. A database can persist an incomplete or contradictory interpretation as successfully as it persists a correct one. The next incidents were about which process was allowed to record the result, when it wrote the result, and what to do when the expected terminal event never arrived.

When dispatch status stopped being useful

Two ways to get the wrong answer

One issue records a run whose provider emitted a completion event while the worker process exited nonzero. The orchestrator rendered the provider event as a completed run. A separate audit path used the process result and recorded failure. Both summaries appeared for the same run. The report proposed consolidating the interpretation and recording disagreements. The important evidence is the actual contradiction and the two paths producing it. The proposed reconciliation should not be presented as a fix that shipped before the subsystem was removed.

A second report reproduced the case where no final result was written. The caller's outer timeout could end the dispatch bookkeeping process. The worker ran in a different process group and survived. A change could proceed all the way through merge and deployment without anyone recording a terminal state for the dispatcher. The status view displayed a failed job with a worker still running. The report documents ten completed issues during a home-automation batch whose records were still classified as failures.

A provider event, an exit code, a pull request, and a deployed service are each useful observations. Their meaning depends on the question. A worker can truthfully say it finished a local task before publication fails. A nonzero exit can indicate failure in teardown or publication after code has already been written. A completed pull request can coexist with an unavailable service. The dispatcher tried to reduce several such observations to one status field. The two incidents show why the field was hard to trust without knowing which stage and source it represented.

Recovery costs and a narrowed decision

A neighboring issue documents temporary GitHub API errors during the same period. Some workers exited early while fetching the issue. Another finished its code and pushed a branch before the pull request step failed. Those runs required different recovery actions. An early failure could justify retrying execution. A published branch without a pull request called for completing the publication step. In both cases an operator could reconstruct state from GitHub and Git, which made the work recoverable while exposing how much coordination was still outside the dispatcher.

The shell process issue and the contradictory terminal status issue were closed during the August reduction. That is a historical choice about the value of repairing the general dispatcher, not evidence that the proposed fixes were shipped. The failing paths still explain the tradeoff. Adding reconciliation, another writer, or a recovery job could have made the old subsystem more accurate. Each addition would have expanded a subsystem the project had begun to rely on less.

The replacement architecture retained specific evidence where it affected an operation the lab still performed. A targeted release checked the running revision. Household actions used persisted approval and task state. The event bus exposed database readiness. The broad status machinery disappeared while narrower checks remained attached to specific boundaries. This is the link between the August failures and the smaller system that followed.

Why six repositories became one

Two overlapping graphs

The lab's original hybrid used Git submodules to pin service revisions. The same directories participated in a pnpm workspace with shared packages and a root lockfile. The Git graph answered which service commit was included. The workspace graph answered which packages and versions could be installed together. A change could be valid in its service repository and still need a parent pin, a compatible materialized checkout, and a consistent workspace before it could ship.

The July architecture decision records two concrete failures. A service branch could advance while the parent still pointed to an old revision. Deployment could then faithfully use the old revision. A guard that rejected stale pointers reduced the risk of shipping it but left the follow-up work in place. An incomplete submodule checkout could cause a root lockfile regeneration to omit workspace importers. A later frozen install could fail even if the original service change had nothing to do with dependency resolution.

The decision counted 176 pointer-update commits in a sample of 300 Lab commits from July 14 through July 30. The ADR notes that a batch bump can mention multiple services, so counts by service cannot simply be added to predict how many commits a migration will remove. The figure is a measurement of that period and method. It shows that source-version coordination had become visible work in its own right, beyond the changes to code and infrastructure that the version updates were intended to carry.

The original lockfile incident is more specific than a missing directory. The submodule status reported the expected commits, while two service worktrees had effectively lost their materialized contents. The workspace resolver operated on what was present and removed the importers. The failure surfaced later inside a Docker build when the full service tree was present again and the frozen lockfile did not describe it. Restoring the trees and checking the expected importer entries before regenerating the lockfile fixed that instance. It also demonstrated that a valid Git pin did not by itself certify the package inputs the build would use.

Alternatives and the migration

The decision compared three options. Keeping the hybrid would preserve separate source repositories and the existing workflow, with continued pointer and workspace reconciliation. A genuinely independent model would remove the submodules, publish shared packages as versioned artifacts, and deploy separately built images through a release manifest. The ADR identified five shared packages with multiple consumers. A change across those packages could have replaced pointer bumps with package releases and dependency updates across repositories.

The monorepo retained the workspace and moved the coupled applications and infrastructure into ordinary directories. A shared library and its callers could change in a single commit. Each service could still have its own image and deployment because those were runtime boundaries. The costs were real. More source moved into one repository-access boundary, the checkout grew, and dependency changes could contend on a shared lockfile. The decision accepted those costs for the coupled lab and kept genuinely independent concerns outside the application monorepo.

Six imports landed in stages. The event bus went first because it had no shared package dependencies. Its import replaced a submodule pointer with files at the same path and preserved the source history. The pull request compared the workspace before and after, reporting the same 19 lockfile importers and a passing frozen install. Keeping paths stable reduced the number of things that had to change at the moment the Git ownership changed.

The last import preserved a standalone backend lockfile for a tool whose backend could be extracted separately from its frontend. That was a deliberate exception to the usual workspace consolidation. After all imports and a normal release from the new layout, the lab removed the pointer-update bot, materialization checks, and deploy-time reconciliation specific to submodules. It kept source revision checks and release recovery. One Git revision could identify the source for a build without a separate parent pin for each service.

From build metadata to an identifiable release

March ship proof

The March commits introduced build SHA and build time into service health responses and passed those values through the image build. A workflow change also emitted image digests and tagged artifacts by source commit. The history contains compatibility tags as well, so a release had both a convenient reference and metadata that could be checked against the source. The goal was to make an operator able to identify a running artifact after a build, a pull, and a container recreation.

This work addressed a basic ambiguity in the earlier flow. A workflow run can report that it built something, and a container can report that it is healthy, without linking the two observations. A workflow may also skip a service under its path filter. The March workflow work took explicit service selection and rebuild inputs into account and made skipped builds visible. The evidence chain was moving from a successful job to a named artifact to a running revision.

A source SHA label is useful for the last step because it can be read from the running image or container. A digest identifies image bytes. A source tag or label communicates the intended relationship to a commit. The later targeted deployment uses the source identity check in its normal path. The history does not establish that every later release used digest pinning from end to end. The early digest work and the later revision check each establish the narrower behavior described in their records.

Why the build moved off hosted CI

An April pull request records roughly 9,500 Actions minutes against a 2,000-minute allowance and describes about $60 in monthly overage. Those are figures from the change record, without a separate billing audit. The proposed reduction focused on work that repeated across the old repository model. A pointer-only pull request could avoid the static and workspace checks intended for source changes. The same change narrowed several service workflows so they would no longer build an image automatically on every merge.

By May the off-Actions runbook described the available billing allocation as exhausted. The documented alternative transferred the relevant source and workspace inputs to a build host, built the image there, and pushed it to the registry with a SHA tag and a source revision label. Deployment could then pull and recreate the service. The runbook separated building and deploying so a previously built image could be inspected or reused. For workspace consumers, including the correct lockfile was part of identifying the build input.

Moving the work off hosted CI changed the cost and failure model. It avoided using hosted minutes for every service build. It also made the lab responsible for the build host, its dependencies, its registry connection, and the state of the source used to start a build. A bounded manual build had operational value even when a fully automatic release path was still under development. The new path supplied a way to distinguish registry availability, artifact identity, and a runtime restart when one of them failed.

The build worker became disposable

The September design moved normal image-building work to a separate machine. The build script streams a clean source archive from the intended checkout. The worker can build and publish an image without maintaining its own long-lived repository clone or storing the household runtime environment. Persistent application data and deployment authority stay with the main runtime. The pull request also retains an explicit fallback build path for recovery if the worker is unavailable.

The separation addresses the shape of the workload. A build can consume CPU, memory, and disk temporarily. A household service needs its state to survive routine restarts and maintenance. A clean source archive gives the worker the inputs it needs for one job and keeps the worker replaceable. The merge record establishes the implementation and its documented prerequisites. It does not provide measurements of build-host availability or sustained performance savings.

What it meant to ship a change

A set of distinct claims

The May release contract recorded stages such as proposed, implemented, open for review, merged, deployed, verified, and shipped. A documentation change could end at a repository operation. A production change required evidence that the deploy had run and that the live result passed the applicable check. A failed verification could produce a rollback, with recovery itself requiring evidence. The vocabulary was an attempt to make claims made by workers correspond to stages the operator could inspect.

The older automation accumulated a large amount of machinery around these distinctions. Some of the value survived the reduction. A merged Git commit is evidence of source state. A published image is evidence that a build artifact exists. The deployment record establishes an attempted change to running state. A container revision check can establish that an instance came from the intended source. A functional probe can establish that a representative operation worked. Each observation supports a different claim, and the later deployment implementation asks for the ones relevant to its scope.

The July proof-of-life work put that into practice. The event bus test wrote a uniquely tagged event and read it back. A journal service test exercised its normal write and read path and compared returned content. A provider routing test obtained an actual response from its configured route. The scripts intentionally asserted on response bodies. The pull request records the examples that ran successfully and separately describes a delegated assistant check that was blocked in the worktree. A failed or unavailable test is part of the historical record of what was demonstrated.

The reload gap

The August home-automation batch exposed a release path that container image identity alone could not cover. Configuration was versioned in the repository, but the live service needed to load it. Workers merged changes and stopped. The operator documented six manual pull-and-reload cycles in the same batch. One change also required a component restart and an integration reload. The initial report proposed an explicit deploy path. The merged follow-ups and closeout then show the one-command path that was actually built and the checks that ran against it.

Configuration changes complicate the meaning of deployment because the authoritative files and the active process can change at different times. Some configuration is reread without a service restart. Other configuration may need a reload or a full restart. The new command classifies changed files. A dashboard or documentation change can be pulled without reloading the service. Automation and template changes can require a reload. Some core configuration changes require a restart. Configuration for an attached service can require both its own restart and a reload of its integration. The operator still has to invoke the command. The closeout explicitly says that an automatic trigger watching the main branch was outside the delivered work.

The verifier compares live entity identifiers and availability across the change. The reason came from a sensor migration where the old platform's registry entry still held the original identifier. The replacement integration registered a second identifier, and downstream templates still referenced the old one. Configuration validation could pass because the files were syntactically valid. A simple count could also miss the meaningful change in identity. The same behavior made a removed template look present when its registry entry remained but became unavailable.

A live round-trip test added a temporary sensor in a merged change, applied the new deploy command, and observed the expected identifier and value from the running system. Removing the test sensor exposed the lingering registry entry. The follow-up made persistent new unavailability fail a reload after a short recheck, while allowing a warning after a full restart where integrations may still be settling. The closeout also records an exercised restart path. The result is stronger than an assertion that a shell command exited successfully. It establishes that a particular configuration change crossed the repository, reload, and live state boundaries.

Targeted and broad deployments

The later operator entrypoint unifies the normal release command. A targeted service release derives the expected revision from the selected checkout. The scripts build or select the image, apply the deployment, and compare the revision of the running container with the intended source. A paired frontend is checked where the service has one. The same check constrains an idempotent skip, because skipping a recreation is safe only when the expected revision is already running and usable.

The September audit found a different contract for deploying the wider infrastructure. The broad path relied on Compose health and could proceed after a registry pull failed, reusing local cached images. It also lacked a single service-specific revision and automatic rollback for the entire stack. The follow-up made an image pull failure fatal for the broad path. The targeted path kept its existing recovery semantics. The patch narrowed a particular false success without pretending a whole-stack change could use the same rollback assumptions as replacing one service.

The maintenance implication is visible in what the lab kept. One operator-facing command reduces the chance that someone follows a retired or incomplete path. An internal Compose helper can still own host-side execution. That layering is purposeful when the outer command owns source and release evidence and the helper owns how containers are changed. The retained distinction makes it possible to diagnose a healthy process running old code without requiring another general deployment dashboard.

How the August reduction worked

The project had already begun retiring services

A May review described applications that incurred a full set of checks, configuration, and deployment work despite contributing little to the active lab. It considered three dispositions. A parked service could stay in the inventory for later use, with most of its maintenance surface intact. An archive could remove its running deployment while preserving a plausible route back. A sunset could remove the service and rely on Git history for the last known state.

The May operator decision approved cleanup for a capability that had already moved into another service and deferred two broader retirements. The July history records subsequent retirement work. One example involved a service whose containers were already gone, while tests, registry metadata, release declarations, and coverage checks still referred to it. The follow-up removed those references. Keeping a stale service in every operating inventory is costly even when no container is consuming memory.

This earlier work explains why the August effort went beyond stopping containers. The active system was represented in service definitions, test discovery, hooks, monitoring, docs, and project tooling. If those surfaces continued to mention a removed service as active, agents could still discover it as work to repair. An archive was therefore partly a change to the operating contract. It took a capability out of the set the lab was expected to maintain.

Removal by use, not by size alone

The August reduction set a stricter standard. The lab would keep what it used to run the household, what protected the household, and applications with continuing use. The work was split into serial changes because the tool that ordinarily dispatched parallel changes was itself slated for removal. Git history was the recovery path for the deleted source. The plan's percentage reduction was a target for non-service tooling. The merged changes provide more precise measurements for the portions they removed.

The main agent-operations change deleted approximately 156,000 lines across 1,263 files. That includes the CLI, agent SDK, dispatch records and governance code, and related material. The figure describes the change, including tests and docs in the deleted surface. It is not an estimate of runtime footprint or human development effort. A separate change reported reducing the central documentation directory from 188 Markdown files to one operations runbook. Service-local documentation and later focused audit files could still exist alongside that runbook.

Some maintenance costs were visible even before a service ran. An August hook cleanup reported cutting the combined commit and push hooks from 1,048 lines to 148 and measured a large improvement for an empty-commit benchmark on that machine. That measurement describes a narrow operation under its stated conditions, not a speedup for every change. The more durable result was deciding which checks had to run before a commit, which had live consumers, and which merely added cost to a common operation.

What earned its place

The follow-up pruning traced callers. The clean service tree check stayed because the build and deploy scripts depended on it. Frontend enumeration stayed where it supplied checks for real applications. A body-asserting production smoke test survived because a successful HTTP status alone had already proved insufficient. These checks were tied to active workflows, with identifiable consequences if removed.

The home-automation cleanup used the same criterion. A custom health signal parsed logs and showed a standing warning for an integration that already exposed its own availability. Removing the wrapper and the derived indicator left the native state as the source of the warning. Other scripts could move to native integrations or templates when they duplicated an existing interface. The cleanup retained the underlying automation and the home-automation platform.

The reduction also had to separate project context from operator configuration. A follow-up plan distinguished Lab-specific knowledge from reusable machine-level instructions and skills. They had been hosted together by the old tooling, but they had different lifetimes and consumers. That plan is evidence of why removing a dispatcher did not mean deleting every artifact used by an agent. Some artifacts belonged next to the project they described. Others belonged to the operator's reusable environment.

Monitoring inside and outside the runtime

The operator reversed a proposed cut

The August plan initially treated an independent uptime monitor as sufficient for the smaller lab. The operating record corrected that assumption. The working off-host monitor was independent of the main system. It could tell whether the host and alert path were reachable when the system that normally emitted alerts was down. A separate configured monitor in the main stack was not the active source of those observations.

The main monitoring stack had a different purpose. It gathered probes of service endpoints, host and container resource metrics, and service logs. It could help distinguish an unavailable host from a live host with an unhealthy dependency or an application failing a specific check. Prometheus and the probe exporters supplied measurements, and log collection gave the operator a way to investigate behavior across restarts or changes. The operator retained both views because either one alone left a blind spot.

The actual monitoring cut removed five Compose services and their associated custom wrappers or checks. The deleted pieces included watchdog and sentinel work that overlapped signals available from the underlying systems or standard monitoring. The pull request records which native metrics remained. The important architectural change was selecting the right source for a signal and maintaining the independent observation path, even during a broad effort to reduce the number of moving parts.

A page is an end-to-end path

An August incident gave the independent path its own failure case. The recovery device's network address changed, while several consumers and published bindings still used the old address. The containers stayed up. The sockets through which the monitoring and notification systems were reached no longer worked, and the issue records four days without alert delivery. The remediation separated the addressing assumptions from the authorization assumptions. A stable reference could repair reachability, while the subsequent permissions change could control who was allowed to publish and read. Neither repair by itself demonstrated that the full alert route delivered a page.

An alert passes through more than a rule evaluation. A producer has to deliver the notification to the alerting service, the service has to accept it, and the intended subscriber has to be able to read it. A probe of the endpoint can establish that the receiver is up. It does not establish that an alert reached the destination. The independent checks included an observation of the alert path, which made it possible to catch failures in the communication system itself.

The August alerting change also made the permission model explicit. Publishing and reading were distinct capabilities, and the system moved to scoped credentials with anonymous access denied. The record describes testing the publishers against the new rules because a forgotten publisher could go silent while other checks still succeeded. The useful public detail is the relationship between permissions and availability. A safe rollout had to verify that valid publishers and readers could still perform their intended actions.

The monitoring stack and recovery host are examples of duplication that served distinct purposes. A host cannot always report its own disappearance. An external monitor cannot diagnose every internal failure from a reachability check. Preserving both was consistent with the reduction because they answered separate operational questions. The wrappers that merely restated a signal available elsewhere were the easier and more defensible cuts.

Backups that looked healthier than they were

The configuration loss in May

One May incident began when a local template replaced a live environment file. The running authentication container continued using a value from the old environment, so the error was latent until the container was recreated. At that point the service had the placeholder instead of the value needed to read its persisted state, and logins failed. An encrypted snapshot of the runtime configuration supplied the value needed for recovery.

The immediate recovery and the prevention mechanism address different points in the incident. Restoring the value fixed the state needed by the service. Comparing the live configuration with a proposed update before applying it detects an unsafe transition. The later sync script checks for a populated live value being replaced by a blank or placeholder value. The check is narrowly about a specific way an operator could lose a working configuration. It does not require a general platform for managing every secret.

The incident also makes the scope of a recovery plan concrete. An image and the application's source are often reproducible. Runtime configuration can contain material that is essential to interpreting existing data and cannot be regenerated from the image. Recovery evidence needs to account for that dependency while keeping the configuration out of public source and ordinary logs. The snapshot in this case was useful precisely because it contained state outside the source checkout.

The logical dump that never ran

The August backup review found a failure in the gate that decided whether PostgreSQL was running. The script had parsed the text intended for a human reading Docker Compose status. The output wording changed, so the check looked for a word the live output no longer contained. The backup job treated a running database as stopped and skipped the logical dump. The repair record reports 105 skip messages and no dump-start messages in the retained log.

That count has a defined scope. It describes the runs present in the log examined in the repair record. It does not show what happened before the retained history or prove that every possible recovery source had failed. It does establish that a running database and an otherwise successful backup operation could coexist with an absent dump for a sustained series of runs. The bug was in a precondition that silently converted failure to collect the dump into a normal skip.

The patch switched to Compose's filtered service output. It exercised the check against the running databases and a negative control. A logical dump of the affected document service's database was also reported during verification. The pull request described the full scheduled backup run as follow-up. This distinction matters because successful detection and a successful manual dump prove the corrected stages individually. They do not by themselves verify every remote archive produced by the complete scheduled job.

An archive with an incomplete inventory

The same review found that a document service stored files in an explicit host mount outside the backup set. Collecting named volumes did not cover that path. Its metadata also lived in a separate PostgreSQL database. The files and database supported one application, but they required different collection steps. A copy of the media alone could leave the restored service without titles, tags, and searchable text. A copy of the database alone would not supply the documents it indexed.

The fix added the relevant mounts and a separate logical dump. It also extended the integrity job to check that expected document media was present in the newest snapshot. That addition changed the question the job could answer. A repository integrity check can show that stored data is readable. A coverage check can catch an important input that never entered the repository. A restore can show whether the pieces that were collected are usable together.

The scripts make further distinctions by storage type. Selected SQLite stores use the online backup API so they can be copied consistently while active. Named volumes and explicit mounts have different inclusion rules. Large recording and log histories are deliberately outside the backup set described by the script. That policy prioritizes irreplaceable application state and the configuration needed to resume service. The existence of an exclusion is an operating choice. An omitted path discovered by a restore investigation is a coverage defect.

Recovering the runtime and the recovery host

Independent monitoring has its own durable state

The recovery host has a different job from the main host. It can observe the main system while the latter is unavailable and provide a path for alerts and recovery. An August audit found that the monitor definitions and alerting state lived only on the recovery device. Its configuration could be represented in source, but some operational state was in local databases. Losing the recovery device could therefore remove the information needed to reconstruct the system that reported failures elsewhere.

The selected approach pulls that recovery state into the existing backup pipeline instead of operating another complete off-site backup system on the recovery device. The scripts create consistent SQLite copies and validate them before including the staged data. The documented tradeoff is that collecting a new copy depends on the main backup host being available. The retained copies are for cold recovery of the monitoring state. The recovery monitor can still observe a main-host outage independently of whether a new backup is being collected at that moment.

A failure to collect the recovery host's state need not discard the backups the main host can still make. The job can continue collecting other inputs and report a failed overall status with the missing component identified. That behavior provides more useful evidence than either silently passing an incomplete run or abandoning every other copy. The same pattern appears in the document database fix. The lab keeps the recoverable output it has while making the incomplete coverage visible.

The recovery-host work does have stronger live evidence for its particular scope. The merge record reports a successful capture and a scratch restore in which the monitoring service started with its restored state. The issue discussion distinguishes that result from the next required observation, a scheduled off-site snapshot containing the recovery subtree. A later closeout reports the backup job operating with the new capture. These are component-level proofs. They establish more than the existence of the script while leaving a full-lab restoration as a separate claim.

Archive checks and restore drills

The backup implementation uses encrypted, deduplicated off-site snapshots. The current timer definitions describe daily backup, weekly integrity checks, and a quarterly restore drill. The restore script unpacks a snapshot into temporary storage, examines key files and databases, and checks restored home-automation configuration in a disposable isolated container. It can exercise real inputs while avoiding changes to the running household system.

These checks form a useful sequence because they answer different questions. A recent snapshot shows the collection job produced an artifact. An integrity check examines the artifacts that entered the archive. Coverage checks compare the artifact against expected inputs. A staged restore checks whether enough data can be read and interpreted to recover meaningful application state. Actual recovery has a further boundary, since it includes applying that state on the intended hardware, bringing services up in order, and observing their behavior afterward.

The September audit found the backup and failure-notification path in code but did not establish recent completion of a restore drill. The timer and drill script are implementation evidence. The May incident is evidence that an earlier snapshot supplied one necessary configuration value during recovery. Neither establishes a recent full restore or an achieved recovery-time objective. Those claims would require a dated run record with its scope, results, and any remaining components restored by hand.

What survived of agent automation

Household approvals are their own system

The household assistant retained a narrower automation policy after the development platform was reduced. An August change explicitly allowed some reversible calendar writes to proceed automatically and recorded them as automatic in the resulting receipts. Destructive changes and external communications retained confirmation. Privileged capabilities had a separate approval requirement. The relevant policy was derived from the capability manifest at the execution boundary, so the same classification could apply regardless of how the tool was invoked.

The durable approval path records the inputs and tool version. Accepting an approval and creating the corresponding task happen as one storage operation. That closes the race in which an approval could be consumed and the process could stop before the task existed. A task can later be recovered as persisted work. At execution time, the implementation checks ownership, expiry, current permission, the tool version, and the input schema again. The approved request and the actual action are connected by state the system can validate.

The action queue also distinguishes a transient network problem from a terminal failure. A bounded retry can be appropriate when the action is still authorized and the cause is temporary. The tests cover rejection when the surrounding context or tool contract changes and a final failure after the permitted retry path. These are specific guarantees for the recorded approval flow. They do not imply that every interaction with every application was migrated to one approval mechanism. The September architecture audit identified remaining parallel paths.

There is a useful distinction between revalidating an approval and deduplicating every side effect of a retry. The approval record and the attempt identifier make the queue's own decisions traceable. An operation that involves an external service still needs to define what happens if the remote side acted before the caller lost the response. The inspected tests establish that the queue can reject an expired or changed request and stop retrying after its configured limit. They do not establish a universal exactly-once property for the integrations the assistant can invoke.

Trust can change during a turn

A September change addressed what happens after the assistant receives text or media from outside the household. The policy uses provenance. If model-visible content came from an untrusted source, subsequent tool calls run under a reduced authority tier for the rest of that turn. Reads can continue. Writes can require fresh approval. Credential use, background work, and delegation are unavailable in that context. The change also covered some tool paths that could otherwise bypass the main registry's policy.

The reasoning is about the inputs a decision may have depended on. A user can authorize reading a page without authorizing instructions found in the page. Subsequent model output may be influenced by that content, so checking only who sent the initial chat message is insufficient. Carrying source provenance through later tool results gives the runtime a signal it can enforce without trying to judge whether a particular sentence resembles an attack.

The merge record establishes the trust policy and focused regression coverage. It does not establish a deployment for every environment or protection against every possible malicious document. The case matters because it makes a narrow authority rule explicit and places enforcement at an operation that can be tested. A small tool surface with a clear decision about writes and delegation is easier to reason about than a broad claim that the assistant is trusted.

A narrower return to repository delegation

The September repository delegation work also preserved a useful part of the older experiment. An operator could request a lab task from chat, approve the request, and later ask for its status. The runner was designed for one job at a time and a draft pull request when a change was warranted. The parent retained publication authority. The child performed the code work in a separate execution context. The merged design did not make this path responsible for automatic merge or deploy.

The pull request lists separate runtime enablement and verification after merge. The September audit also records a deliberate limitation. The initial task-status map was process-local, so a restart could lose the status view. The implementation can therefore be described as a bounded delegation mechanism with a documented failure mode. It cannot be used as proof that the broader autonomous development system had returned or that durable execution was established across arbitrary tasks.

Compared with the old dispatcher, the new contract ended at an inspectable repository artifact. The operator could see whether the draft existed and assess its contents through ordinary GitHub workflow. That narrower endpoint reduced the number of claims the runner had to make about testing, release, and production state. The history shows a decision to retain useful execution and approval boundaries while giving the surrounding workflow a smaller scope.

The September audit and the smaller lab in use

Reliability changes after the cut

The September audits distinguish the reduction from the end of engineering work. The event bus kept a separate readiness check because its database was essential. The household assistant could still serve native capabilities if optional skill rehydration failed, so a follow-up exposed degraded capability state without treating every missing skill as a process failure. A scheduler that was expected to persist jobs stopped silently substituting an in-memory scheduler when its configured store could not start.

The household task runner also had a restart gap. It inspected running tasks once at startup but only treated tasks beyond a configured age as abandoned. A quick restart could leave a task marked running without a process to execute it or a later recovery pass to reconsider it. In the single-executor design, an inherited running row necessarily belonged to the previous process. The fix marks such rows as failed immediately on startup so the operator or workflow can handle them explicitly. The rule depends on the single-executor assumption. A different topology would need evidence of ownership across processes.

These changes point to several meanings of health within one installation. A process can be live while a required database is unusable. An optional capability can be missing while the rest of an assistant is available. A scheduler can accept work while failing to preserve it across restarts. A running task record can outlive the only process that owned it. The audit and fixes identify the specific degraded state and choose how visible it should be at the boundary that depends on it.

The audit's smaller proposed changes followed the same principle. It recommended correcting dependency readiness, distinguishing optional degradation, and making the status of a supposedly persistent scheduler visible. It also identified generalized frameworks and overlapping compatibility paths for review. Those recommendations have different evidence from the fixes that landed. A candidate for deletion in an audit remained a candidate until the repository or a runtime check established what happened to it.

October and November records

The October history shows maintenance of concrete household behavior. One automation observed a playback service that was busy at its single scheduled trigger and correctly declined to interrupt it. The service became idle shortly afterward, but the automation had no second chance to start. The fix added bounded retries over a limited time window while retaining non-interruption checks. A persistent session marker prevented a second start after a manual pause or a Home Assistant restart. The pull request reports test coverage and describes observing a naturally scheduled run as a separate live verification step.

The same series includes fixes to integration compatibility and waiting for observed state before advancing a fade. These changes are smaller in scope than the early platform plans. They still require careful reasoning about device state, external service changes, and operator intent. The key evidence is the October change record and what it says about the original behavior, not an inference from the existence of a configuration file alone.

The November snapshot contains a routing change for an adjacent household application. It shows that the lab still served as an integration point even after much of the former platform was removed. The change does not establish where all of the application's processing ran, how often it was used, or which unrelated lab services were enabled. It is one more example of the narrower work visible in the later record.

The surviving operations path can be described from the main branch and dated records. Home automation, service-specific releases, independent checks, and recovery continued to have source and operational changes. The number of declared Compose services is not a live inventory. The last recorded commit is not proof of current uptime. The smaller shape is supported by the documented retirements, the surviving runbook, and the kind of fixes that continued to land.

Synthesis and limits of the evidence

Where the architecture simplified

The lab repeatedly found a difference between evidence produced by a component and evidence for the outcome the operator cared about. A dispatcher could know a provider had stopped sending events without knowing whether a branch was published. A workspace could install correctly with one set of submodules and fail with another. A backup archive could verify cleanly even though a separate database was missing. A health check could return success without proving a service could write its primary store.

The changes that lasted generally brought the check closer to the action or state it represented. The monorepo put coupled release inputs in a single source revision. The deployment check read identity from the running container. The event bus checked database readiness and kept event storage separate from live delivery. The backup check asserted expected contents, while the restore drill exercised a separate recovery path. The retained approvals were validated again where the action could actually run.

Some apparent overlap remained because it served different purposes. A service-specific health check and an off-host uptime check operate under different failure conditions. A durable record and a live stream give different guarantees. A source repository and a runtime container can be separate architectural units even after the source tree is consolidated. The useful distinction throughout this history is whether two mechanisms record the same truth twice or observe different things that an operator needs to know.

The large reduction can therefore be understood as an operational decision as much as a source cleanup. The project stopped maintaining a general dispatcher and large bodies of governance machinery. It kept mechanisms that were exercised by household services and specific software changes. Later repairs were small enough to identify the affected boundary, the evidence that failed, and the behavior to test. That is a clearer way to describe the smaller lab than a single count of containers or files.

What remains unmeasured

The record supports several dated figures, including the July pointer-update sample, the size of the August deletion, and the backup skips reported in the retained log. Each measures a different thing. None gives a reliable estimate of personal time saved, total operating cost, or the production success rate of autonomous work. The April billing numbers were reported in the change record and describe one period of hosted CI usage.

The source establishes how services are configured and how particular fixes were implemented. It cannot establish a fresh end-to-end restore, current hardware utilization, or the present state of every integration. A runbook entry is a procedure. A timer definition is a schedule. A dated report of a live test is stronger for the operation tested, with the usual limits of its sample. The project evidence ends at the November snapshot used for this account.

The underlying repository and historical work records are private. The source notes identify the dates and types of primary records that support each part of the account. The technical findings are presented at the level necessary to understand the design and the changes it underwent.
